# Acceptance matrix: Zlatura (from Comp Loader 3.3.0)

Baseline: `main` at the merge of pull request #3 (content identical to commit
`8ddc4e9`), version 3.3.0, audited 2026-10-10. Updated through Phase 1
checkpoint (c), version 4.2.0 (in review). This file tracks every feature
in the Zlatura development brief. It supersedes `docs/ACCEPTANCE.md` (the 3.2.0
matrix), which stays as the detailed record of how 3.2.0 was tested.

## Status vocabulary (brief, Part 23)

| Status | Meaning |
|---|---|
| Implemented and verified | Built, tested at the level stated, evidence named |
| Implemented, not fully tested | Built; test gaps listed |
| Tested with synthetic fixtures only | No real-world document or service validation |
| Tested with live services | Real provider calls verified; date and method recorded |
| Blocked | Missing credentials, infrastructure or access (stated) |
| Partially implemented | What exists and what is missing |
| Not implemented | Not started |

"Synthetic fixtures" means the invented OMs, CoStar reports, rent rolls and
workbooks generated by `tests/e2e/make_pdfs.py`, `make_tpl.py`, `make_model.py`
and `tests/fixtures.js`. No real brokerage file has been used. No test has run in
Safari, Firefox or Microsoft Excel; workbooks are recalculated in LibreOffice.

Evidence names: unit tests are `tests/*.test.js` (157 pass at 4.2.0); browser flows are
`tests/e2e/*.mjs` run by `tests/e2e/run.sh` (24 flows at 4.2.0 plus LibreOffice
recalculation of 9 exported workbooks; all pass on the baseline).

## Part 2–3. Pillars and architecture foundations

| Feature | Status | Notes |
|---|---|---|
| Typed domain model with unit-branded types | Not implemented | Plain JS objects today. Decided: JSDoc types checked by `tsc --checkJs`, no build step, no switch to TypeScript. |
| Explicit missing values (`unknown` / `not_applicable` / `confirmed_zero`) | Partially implemented | Analysis treats missing as `null`, never 0 (`deal.js`). Stored deals use absent keys and `null`; there is no `confirmed_zero` or `not_applicable`. |
| Decimal or integer-cent money | Implemented and verified | Checkpoint (b), 4.1.0. Stored totals are rounded to whole cents and rates per SF or unit to four decimals (`app/engine/money.js`), as rounded numbers rather than integer cents, so the saved shape is unchanged. Computed figures stay in floating point. Existing values are rounded once, each logged old → new and shown in Settings → Your data. `money.test.js`, `engine-flow` (restores a 3.3.0 backup with sub-cent values: 4 values rounded and listed). Not checked on any real device's data. |
| Pure calculation engine, one formula per quantity | Partially implemented | Checkpoint (b): WALT, debt service, net effective rent, break-even occupancy and the comp rules each have one function in `app/engine/`, used by every screen, tool and workbook formula (D2–D6, D8 fixed; `engine.test.js`: 11 known answers, 9 fail on 4.0.0; LibreOffice checks the Excel formulas against the engine). Other math is still spread over `calc.js`, `deal.js`, `lease.js`, `tools.js`. |
| Calculation results carry inputs, formula id, conventions, warnings | Not implemented | |
| Convention registry, configurable | Partially implemented | Checkpoint (b): `app/engine/conventions.js`, listed in Settings → Calculation conventions. WALT weighting and month-to-month treatment are settable, kept on the device, and every WALT label follows them (`engine-flow`). The other conventions are listed but fixed. |
| Impact Graph (dependency graph, "this change affects…", cycle detection) | Not implemented | |
| "Explain this number" for every material output | Partially implemented | Deal figures show source tags (OM page, typed, edited, derived, AI, tool, scenario); tools have "How it is worked out". No general drill-down. |
| Event-sourced change history | Partially implemented | 4.3.0, checkpoint (d) part A. Each deal keeps a history of every action as an entry: what changed, old and new, with a plain-English label. It is written in the same IndexedDB transaction as the deal save, so the two are saved together or not at all. The deal record itself is still saved whole, so this is a change log beside it, not a store that rebuilds the deal from events. `history.test.js` (including 400 random round trips) and `history-flow`. |
| Undo/redo for all deal edits | Implemented and verified | 4.3.0. Undo and Redo are per deal, with buttons that name the action and Ctrl/Cmd Z and Shift Ctrl/Cmd Z (Ctrl Y). There are 100 steps, kept across reloads, plus "Undo to here" in History. An undo is refused if a value it would change has changed since. Rounding entries are never undone. Removed photos and recordings are kept 30 days. `history-flow`, `snapshot-flow`, `history.test.js`. Tested in Chromium only. |
| Snapshots (named and automatic), compare, restore | Implemented and verified | 4.3.0, checkpoint (d) part B. Up to 20 named and 10 automatic snapshots per deal. Automatic ones are taken before an import, Tools or AI applied, a snapshot restore, and a backup restore that overwrites the deal. Compare lists each difference; restore is one step you can undo. An import too large to undo step by step undoes from its snapshot. `snapshot-flow`. |
| Backups carry history and snapshots (version 2); version 1 still restores | Implemented and verified | 4.3.1, checkpoint (d) part C. Included by default, with an option to leave them out. A restore combines the backup's history with the device's by entry id, in time order, so nothing is overwritten. Version 1 files (4.2.1, 3.3.0) restore, with the deal's history starting at the restore. `backup.test.js` (version 2 round trip, without history, version 1 read, newer version refused, restore plan) and `limits-flow`. |
| Storage limits and the 80% warning | Implemented and verified | 4.3.1, part D. Per deal: 1,000 entries or 2 MB of history, oldest first, with "History kept since …". Overall: 50 MB, never above half the browser's quota; automatic snapshots go first, then the oldest history, then removed media; named snapshots are never removed. Settings shows the sizes and warns from 80% of that space, or of the browser's own quota. Clear a deal's history from its History. Sizes are kept in one record, written with each change and counted again if missing (a 4.3.0 database). `limits-flow` (quota stubbed to 6 MB). Not tested against a real full device. |
| Database version 2 (history, snapshots, trash) without data loss | Implemented and verified | `upgrade-flow`: a 4.2.1 database with a deal, a photo, a task and a backup upgrades with nothing changed or lost, byte for byte. An older tab holding the database gets "close or reload that tab"; a tab outdated by a newer version gets "Reload to finish updating", and its edits are kept in the recovery copy. The 4.2.1 backup restores. Chromium only. |
| Versioned schema with forward migrations and a migration test suite using real old backups | Partially implemented | One lazy migration (rent roll schema 2). No migration registry. |
| Local-first with optional cloud sync | Partially implemented | Local-first only; no sync. |
| Plugin interfaces (parsers, calculators, template adapters, exports, data providers) | Not implemented | Tools are declared as data (`toolsdefs.js`), the closest existing pattern. |
| REST API and webhooks | Not implemented | |
| Performance budgets measured | Implemented, not fully tested | Checkpoint (c), 4.2.0, `perf-flow` (in `run.sh`), headless Chromium in this container, medians of 5. A 500-lease rent roll opens in 189 ms (4.1.0: 1,843 ms; budget 1 s). An edit shows its totals in 66 ms (4.1.0: 1,065 ms; budget 150 ms). With the CPU slowed 4×, it opens in 814 ms (met), but an edit takes 326 ms (**not met**). Not measured on a real phone, or in Safari or Firefox. The 500 leases are generated. |
| Long work off the UI thread | Partially implemented | pdf.js parses in a worker. Since 4.2.0, the lease projection for every screen runs in a module worker (`app/projector-worker.js`), with a fallback onto the page if it can't load (`bigroll-flow`), and long rent rolls draw only the rows near the screen. OM analysis, exports and template fills still run on the main thread; the projection they use is now 14× faster. |
